为什么需要 Embedding —— 关键词检索的天花板

一个具体的失败案例

用户问："怎么把路由器恢复初始设置"

知识库里正确答案的标题是："如何重置路由器密码与还原出厂配置"

传统倒排索引 / BM25 靠词面重叠。两句话的交集词：

query 词: {怎么, 把, 路由器, 恢复, 初始, 设置}
doc   词: {如何, 重置, 路由器, 密码, 与, 还原, 出厂, 配置}
交集 = {路由器}  → 命中信号极弱
"恢复初始设置" ≈ "还原出厂配置"，但 0 个词对得上

同义改写、上下位词、跨语言 —— 关键词检索全都看不见。

Embedding 的核心主张

把每段文本映射成一个固定长度的实数向量 v ∈ ℝd（d 常见 384 / 768 / 1024），并使得：

语义相近的文本  ⟺  向量在空间里距离近

于是"找相关内容"这件事，从字符串匹配变成了几何最近邻搜索。同义、改写、跨语言都被编码进同一个连续空间里。

注这就是 JD 里"Embedding 原理 + 向量数据库 + 知识召回"三件事的共同地基 —— 后两者都建立在"文本已经是向量"这个前提上。

JD 三块知识怎么层层依赖（这是知识分层，不是一次请求的运行时顺序）

一句话是怎么变成一个向量的 —— 4 步管线

整体管线

① Tokenize —— 文本不是 LLM 的输入，token id 才是

用 BPE / WordPiece / SentencePiece 把字符串切成子词，再查词表换成整数 id。中文常按字 + 高频词混合。

// 概念示意
"重置路由器密码"
  → ["重","置","路由","器","密码"]
  → [ 7028, 9210, 4501, 3322, 5439 ]   // token ids
  → 前后补 [CLS]/[SEP] 等特殊 token

每个 id 进入一个可训练的查找表 E ∈ ℝ|V|×d，得到初始（静态、无上下文）词向量。

② Transformer —— 让向量"带上下文"

关键：同一个词在不同句子里应当是不同的向量。"苹果发布会" vs "吃苹果"里的"苹果"必须分开。

self-attention 让每个 token 的表示成为全句的加权汇总：

Attn(Q,K,V) = softmax( Q K⊤√dk ) V

叠 N 层后，第 i 个位置的输出 hi 已经"读过"整句话 —— 这就是 contextual embedding，是语义相似度的来源。

③ Pooling —— L 个 token 向量压成 1 个句向量

方式做法谁在用
mean对所有 token 向量取平均（含 mask）BGE / E5 / sentence-transformers 主流
CLS直接取 [CLS] 位置的向量早期 BERT 类
last-token取最后一个 token（解码器架构）LLM 系 embedding（如 gte-Qwen）

mean pooling 的公式（mi 是 attention mask）：

v = ∑i=1L mi · hi ∑i=1L mi

④ L2 归一化 —— 把向量钉到单位球面

v̂ = v‖v‖2 ，  ‖v‖2 = √(∑ vi2)  ⟹  ‖v̂‖ = 1

归一化后有一个极重要的结论：

a·b （点积）= cos(a,b) ，  ‖a−b‖2 = 2 − 2·cos(a,b)

关键三种度量在归一化后排序完全等价。这就是为什么向量库默认存归一化向量、用内积索引 —— 既快又和余弦一致。下一节用真实数字证明。

实战前置：真实输入不是一句话，是长文档 —— embed 前必须先「分块」

上面那张「整体管线」图从 "重置路由器密码" 这种一句话讲起，是简化。真实场景你拿到的是 50 页 PDF / 一篇 wiki。直接整篇 embed 会出两个致命问题：

  • 超长被截断：embedding 模型有最大输入（BGE-large 512 token、bge-m3 8192 token），超出部分直接丢，尾部内容根本没进向量
  • 语义被平均稀释：整篇 → 1 个向量，等于把几十个主题求平均，检索时什么都沾一点、什么都不精确，召回率暴跌

所以 embed 之前要先把文档切成段落级 chunk，每个 chunk 一个向量。下面是真实流程图与可手算的参数。

四个核心参数（必须能解释）

参数含义 / 典型值
chunk_size每块最大长度。单位是 token，不是字符，且要用该 embedding 模型自己的 tokenizer 数。典型 256–512 token（中文约 400–800 字）
chunk_overlap相邻块重叠长度，防边界切断。典型取 chunk_size 的 10–20%（512 → 50–100）
separators切分优先级：段落 \n\n > 句号 。！？ > 逗号 > 空格 > 单字。尽量让边界落在自然停顿
length_function量长度的函数。用 tokenizer.encode 数 token；别用 len(str)——中文1字≈1–2 token、英文1词≈1.3 token，差很大

分块策略（从糙到精）

策略说明
fixed-size定长硬切。最简单，最容易切断语义
recursive-character工程默认：按 separators 优先级递归切，块超长才降级用更细的分隔符
sentence / 结构感知按句子或 Markdown 标题/代码块切，边界更自然
semantic用 embedding 算相邻句相似度，相似度骤降处断块（最准、最贵）
parent-child
(small-to-big)		小块用于检索（精准），命中后回填它所属的大块/父段喂给 LLM（上下文全）

伪代码 · recursive-character 切分 + overlap + 入库

def split_text(text, chunk_size=512, chunk_overlap=64,
               separators=["\n\n", "\n", "。", "！", "？", " ", ""]):
    tok = embedding_model.tokenizer            # ← 关键：用 embedding 模型自己的分词器
    n_tok = lambda s: len(tok.encode(s))

    # 1. 递归切：当前分隔符切完仍超长，就降级到更细的分隔符
    def recurse(s, seps):
        if n_tok(s) <= chunk_size:
            return [s]
        sep, rest = seps[0], seps[1:]
        parts = s.split(sep) if sep else list(s)
        out, buf = [], ""
        for p in parts:
            cand = (buf + sep + p) if buf else p
            if n_tok(cand) <= chunk_size:
                buf = cand
            else:
                if buf: out.append(buf)
                out += recurse(p, rest) if (rest and n_tok(p) > chunk_size) else [p]
                buf = ""
        if buf: out.append(buf)
        return out

    raw = recurse(text, separators)

    # 2. 加 overlap：每块前面拼上一块尾部的 chunk_overlap 个 token
    chunks = []
    for i, c in enumerate(raw):
        if i > 0:
            tail = tok.decode(tok.encode(raw[i-1])[-chunk_overlap:])
            c = tail + c
        chunks.append(c)
    return chunks

# 3. 每个 chunk 连同【原文 + 元数据】一起入库 —— 向量只是检索用的“钥匙”
for i, ch in enumerate(split_text(doc.text)):
    vec = embedding_model.encode(ch, normalize=True)   # ← §1 ①~④ 那条管线
    vector_db.upsert(
        id=f"{doc.id}#{i}",
        vector=vec,                                  # 只用来“找”
        payload={                                    # 真正要回传给 LLM 的东西
            "text": ch,                             # ← chunk 原文（关键！见 §6）
            "doc_id": doc.id, "title": doc.title,
            "source": doc.url, "chunk_index": i,
        })

承接 §6入库存的是 (向量, payload) 对。向量只用于"找"，真正喂给 LLM 的是 payload 里的 chunk 原文 —— 这点最容易搞混，§6 末尾用实际调用代码讲透。

cosine / dot / L2 —— 几何直觉 + 完整手算

三个公式

余弦相似度（关心方向，∈[−1,1]）
cos(a,b) = a·b ‖a‖·‖b‖ = ∑ aibi √∑ai2 · √∑bi2
点积 / 内积（方向 + 长度）
a·b = ∑i ai bi
欧氏距离 L2（越小越近）
‖a−b‖ = √( ∑i (ai−bi)2 )

选哪个文本检索几乎总是 cosine（长度不该影响语义）。向量库里常配合 L2-normalize 后用 dot，结果与 cosine 一致但更快。

2D 几何：余弦就是"夹角"

例 1 · 把上面的图一步步算出来（2 维，便于手验）

// A=(1,0)  B=(0.7,0.7)  C=(0,1)  D=(−1,0)

cos(A,B) = (1·0.7 + 0·0.7) / ( √(1²+0²) · √(0.7²+0.7²) )
         = 0.7 / ( 1 · √0.98 )
         = 0.7 / 0.98995
         = 0.7071            → 夹角 45°（B 在 A 和 C 正中间）

cos(A,C) = (1·0 + 0·1) / (1 · 1) = 0 / 1 = 0          → 正交，90°，完全无关

cos(A,D) = (1·(−1) + 0·0) / (1 · 1) = −1      → 反向，180°，语义相反

读法：cos = 1 同义 / 复述；cos ≈ 0.7~0.9 强相关；cos ≈ 0 不相关；cos < 0 在文本检索里基本不出现（好的 embedding 把无关项压到 0 附近而非负）。

例 2 · 三种度量给出同一个排序（证明"归一化后等价"）

取归一化向量 a=(0.8,0.6)，b=(0.6,0.8)，两者都在单位圆上：

dot  a·b   = 0.8·0.6 + 0.6·0.8 = 0.48 + 0.48 = 0.96
cos  a·b/(‖a‖‖b‖) = 0.96 / (1·1)        = 0.96   // 归一化后 = dot
L2   ‖a−b‖² = (0.8−0.6)² + (0.6−0.8)² = 0.04+0.04 = 0.08
       ‖a−b‖  = √0.08 = 0.283
       验证恒等式: ‖a−b‖² = 2 − 2cos = 2 − 2·0.96 = 0.08  ✓

结论cos 越大 ⟺ dot 越大 ⟺ L2 越小，三者排序严格一致。所以向量库选内积索引、存归一化向量，是性能与正确性的双赢，不是近似。

这个空间是怎么"学"出来的 —— 对比学习 / InfoNCE

训练信号：拉近正样本，推开负样本

预训练语言模型本身不天然产生好的句向量（直接 mean-pool BERT 效果很差）。Embedding 模型靠对比学习微调：

  • anchor a：一个 query / 句子
  • positive p：与 a 语义相同（同义改写、问答对、标题-正文）
  • negatives nj：无关文本，尤其是 hard negative（看着像但其实不对）

目标：让 sim(a,p) 远大于所有 sim(a,nj)。

几何上发生了什么

InfoNCE 损失（对比学习的标准损失，必背）

ℒ = − log exp( s(a,p) / τ ) exp( s(a,p) / τ )  +  ∑j exp( s(a,nj) / τ )

本质就是一个"正样本对 vs 一堆负样本"的 softmax 分类交叉熵：把 a 正确"分类"到 p 上。s 是相似度（通常归一化后的点积），τ 是温度系数（典型 0.05 ~ 0.1），τ 越小对"难负例"的惩罚越尖锐。

例 · 好分离的样本 → loss 极小

// s(a,p)=0.9  s(a,n₁)=0.2  s(a,n₂)=0.1  τ=0.1
exp(0.9/0.1) = exp(9)  = 8103.08   // 分子
exp(0.2/0.1) = exp(2)  =    7.389
exp(0.1/0.1) = exp(1)  =    2.718

分母 = 8103.08 + 7.389 + 2.718 = 8113.19
ratio = 8103.08 / 8113.19      = 0.99875
ℒ = −ln(0.99875)               = 0.00125

正样本相似度远高于负样本 → 概率≈1 → loss≈0 → 几乎没有梯度，模型"已经学会了"。

例 · 难负例混淆 → loss 巨大 → 强梯度

// s(a,p)=0.3  s(a,n₁)=0.8  s(a,n₂)=0.7  τ=0.1
// 负样本反而比正样本还像 —— hard negative
exp(0.3/0.1) = exp(3) =   20.09    // 分子
exp(0.8/0.1) = exp(8) = 2980.96
exp(0.7/0.1) = exp(7) = 1096.63

分母 = 20.09 + 2980.96 + 1096.63 = 4097.68
ratio = 20.09 / 4097.68          = 0.00490
ℒ = −ln(0.00490)                 = 5.318

大梯度loss 从 0.001 飙到 5.3，反向传播会狠狠调整参数，把 p 拉近、把 n₁/n₂ 推远。hard negative 的质量直接决定 embedding 上限 —— 这是面试高频追问点。

纯向量检索基线 —— 一次查询从 query 到答案的手算全过程（无 BM25 / Rerank）

场景设定

知识库 3 条文档，用户问 "路由器密码忘了怎么办"。为了能手算，这里用 4 维可解释维度演示。

重要免责真实 embedding 是 768/1024 维且每一维不可解释（不是"路由器维""金融维"）。这里强行给维度命名只为让你能用笔验证算术 —— 几何与排序逻辑和真实情况完全一致，不要对外宣称 embedding 维度有语义。

向量文本维度①路由器维度②密码/重置维度③出厂设置维度④金融
qquery：路由器密码忘了怎么办0.90.80.50.0
d₁如何重置路由器密码0.90.90.20.0

步骤 A · 算模长（√平方和）

‖q‖  = √(0.9²+0.8²+0.5²+0²) = √(0.81+0.64+0.25+0)  = √1.70 = 1.3038
‖d₁‖ = √(0.9²+0.9²+0.2²+0²) = √(0.81+0.81+0.04+0)  = √1.66 = 1.2884
‖d₂‖ = √(0.8²+0.3²+0.9²+0²) = √(0.64+0.09+0.81+0)  = √1.54 = 1.2410
‖d₃‖ = √(0²+0²+0²+1²)       = √1.00                       = 1.0000

步骤 B · 算点积（逐维相乘再相加）

q·d₁ = 0.9·0.9 + 0.8·0.9 + 0.5·0.2 + 0·0  = 0.81 + 0.72 + 0.10 + 0 = 1.63
q·d₂ = 0.9·0.8 + 0.8·0.3 + 0.5·0.9 + 0·0  = 0.72 + 0.24 + 0.45 + 0 = 1.41
q·d₃ = 0.9·0    + 0.8·0   + 0.5·0   + 0·1  = 0                       = 0.00

步骤 C · 算余弦相似度（点积 / 模长积）

cos(q,d₁) = 1.63 / (1.3038 · 1.2884) = 1.63 / 1.6799 = 0.9703
cos(q,d₂) = 1.41 / (1.3038 · 1.2410) = 1.41 / 1.6180 = 0.8714
cos(q,d₃) = 0.00 / (1.3038 · 1.0000) = 0             = 0.0000

步骤 D · 用 L2 距离交叉验证（应给出相同排序）

‖q−d₁‖² = (0.9−0.9)²+(0.8−0.9)²+(0.5−0.2)²+0 = 0+0.01+0.09+0 = 0.10 → ‖·‖=0.316
‖q−d₂‖² = (0.9−0.8)²+(0.8−0.3)²+(0.5−0.9)²+0 = 0.01+0.25+0.16 = 0.42 → ‖·‖=0.648
‖q−d₃‖² = 0.81+0.64+0.25+1.00                                 = 2.70 → ‖·‖=1.643

cosine 大的 ⟺ L2 小的：两套度量给出完全一致的排名，印证了 §2 的结论。

步骤 E · 排序 → Top-k → 喂给 LLM

排名文档cosineL2判定
1d₁ 如何重置路由器密码0.9700.316最相关，必进上下文
2d₂ 路由器恢复出厂设置步骤0.8710.648相关，作为补充

这是 §4 的纯向量基线（只用 §2 的 cosine 排序，未引入 BM25 / Rerank）。后面两节是对它的两种"放大"，不是在它后面接新阶段：§5 把「向量库 · 最近邻检索」这一格拆开 —— 亿级数据下怎么靠 ANN（HNSW / IVF-PQ）做到毫秒召回；§6 说明真实 RAG 不止这一条腿 —— 在 ANN 这条稠密腿旁边再并联一条 BM25 稀疏腿，RRF 融合后再 Rerank、最后缝合进 prompt。务必分清ANN 是「混合检索」内部的一条腿，不是它前面的独立一步；§6 流程图才是运行时的准确层次，本图只是入门基线。

向量库 —— 句向量存成什么样、检索怎么找回原文、为什么还快

先回答：句向量存成什么形式？检索时怎么知道对应哪句原文？

这两个问题是同一件事的两面，答案就一句话：

核心embedding 不可逆——768 个浮点是语义指纹，不能像 detokenize 那样还原成文字。所以"找回原文"不靠反解向量，而靠：写入时把向量和原文塞进同一条记录、绑同一个 id；检索时 ANN 只在向量字段上算距离、返回 id，再用 id 回表取原文。向量负责"像不像"，id 负责"是哪条"。

一条记录的真实样子

{
  "id": "doc42#7",                 // 主键：第 doc42 篇的第 7 个 chunk
  "vector": [0.0132, -0.0871,    // 768 个 float32（§1 ①~④ 产出）
             0.0444, ... ,        // 已 L2 归一化，‖v‖=1
             0.0095],
  "payload": {
    "text": "忘记密码时，长按机身 reset 键约 10 秒…",  // ← 原句
    "doc_id": "doc42",
    "title": "TP-Link 路由器手册",
    "source": "https://…/manual.pdf#p12",
    "chunk_index": 7
  }
}

逻辑上就是一张表的一行：主键 id 列 + 向量列(float32[d]) + JSON payload 列。

检索回程（注意 ANN 返回的是 id）

qvec = embedding_model.encode(query, normalize=True)
res  = vector_db.search(qvec, top_k=5)
# res 只有 id 和距离，没有向量、没有文本：
#   [ {id:"doc42#7", score:0.91},
#     {id:"doc11#2", score:0.87}, … ]

for r in res:
    rec  = vector_db.get(r.id)      # 用 id 回表取整条记录
    text = rec.payload["text"]   # ← 这才拿回原句
    # text 拼进 prompt（§6）

向量做"像不像"的排序，id 做"是哪条"的回表 —— 两者缺一不可。

工程现实"检索怎么知道对应原文" = 有没有人把 id→原文 的映射存好：
· 裸索引（FAISS / hnswlib / numpy）：只存 id ↔ vector，没有 payload 概念 → 你必须自己另存一份 id → 原文 映射（dict / SQLite / 一张表），检索回 id 后自己 join。漏了这步，就是"检索到了却不知道是哪句"的根因。
· 托管向量库（Qdrant / Milvus / Weaviate / pgvector / ES kNN）：原生支持 payload 与向量同存，search 直接把原文随 id 一起返回，省掉手动 join。

先看暴力检索为什么不行

"找最近邻"最朴素的做法：query 和库里每一个向量都算一次距离，排序取 Top-k。这叫 Flat / brute-force。

代价 = O(N · d) 每次查询 
// 1 亿条 × 1024 维 float32
存储 = 1e8 × 1024 × 4 B   ≈ 400 GB
单次查询乘加 = 1e8 × 1024 ≈ 1e11 次
// 单机几秒~几十秒一条 query —— 线上不可接受

Flat 召回率 100% 但不可扩展。ANN（近似最近邻）用极小的召回损失换 100~1000× 加速：recall@10 仍能 ≈ 0.95+。

ANN 的核心权衡三角

所有向量库（FAISS / Milvus / Qdrant / pgvector / ES kNN）都在这个三角里取舍。两大主流索引：HNSW（图）和 IVF-PQ（聚类 + 量化）。

HNSW —— 多层近邻图，"高速公路 + 市区小路"

搜索过程：从顶层唯一入口进 → 在当前层贪心走向离 query 更近的邻居，走不动就下沉一层 → 到第 0 层用宽度 efSearch 的优先队列做局部最优搜索 → 回溯出 Top-k。每次跳转把候选集缩小一个数量级，复杂度 ≈ O(log N)。

参数含义调大的后果
M每个点的邻居（边）数图更密 → 召回↑、内存↑、构建慢
efConstruction建图时候选队列宽度图质量↑、建索引慢
efSearch查询时搜索宽度召回↑、延迟↑（线上主旋钮）

特点召回高、延迟低，是中小规模（千万级）默认首选；缺点是内存大（图结构 + 全精度向量都在内存），删除是软删除需周期重建。

IVF-PQ —— 倒排分桶（少搜）+ 乘积量化（压小）

IVF：只搜最近的几个簇

先对全库向量跑 k-means 聚成 nlist 个簇（Voronoi 单元）。查询时只在离 query 最近的 nprobe 个簇里找：

nlist  = 4096   // 把库切成 4096 桶
nprobe = 16     // 只搜最近 16 桶

搜索量 ≈ 16 / 4096 ≈ 0.39% 的数据
→ 理想约 250× 加速（nprobe 越大越准越慢）

PQ：把向量压成几十个字节

把 d 维向量切成 m 段，每段用 256 个质心的小码本量化成 1 字节：

d = 1024, m = 64  // 每段 16 维
原始 = 1024 × 4 B = 4096 B
PQ   = 64 × 1 B   =   64 B   // 压缩 64×
// 距离用码本查表近似(ADC)，不还原原始向量

特点内存极省、能上十亿级；代价是 PQ 量化引入误差、召回略低于 HNSW，常用 重排（用原始向量对 PQ Top-N 再精算一次） 找回精度。选型口诀：千万级求精度 → HNSW；十亿级 / 内存吃紧 → IVF-PQ；要兼顾 → HNSW-PQ / DiskANN。

用向量库时必须和 Embedding 侧对齐（接 §1、§7）

  • 度量一致：embedding 训练用 cosine，库就建 cosine/内积索引；建库存的是否归一化要和查询端一致 —— 不一致 = 检索全是噪声
  • 维度一致：换 embedding 模型必须全量重建索引，新旧向量不可混存
  • 带过滤的 ANN：真实业务常要 "category=A 且 时间>X 再做近邻"，注意 pre-filter / post-filter 对召回率的影响
  • 增量：HNSW 支持在线插入、删除是软删；IVF 大批量增量后质心会漂移，需定期重训

知识召回策略 —— 混合检索（RRF）+ Rerank（精排）

为什么纯向量召回还不够

向量检索擅长语义，但有结构性盲区：

  • 精确词：型号 "iPhone 15 Pro"、错误码 "ORA-00904"、人名、API 名
  • 数字 / 单位 / 罕见专名 —— 语义向量会把它们"抹平"

关键词检索 BM25 正好相反：精确匹配强、语义弱。两者互补 → 混合检索 = 同时跑 dense（向量）+ sparse（BM25），再融合。

BM25 ∝ ∑t∈q idf(t) · tf(t,d)·(k₁+1)tf(t,d)+k₁(1−b+b·|d|/avgdl) tf 饱和 + 长度归一

融合用 RRF，不用"加权分数"

向量分（cosine 0~1）和 BM25 分（无上界）量纲不同，直接加权很脆。RRF（Reciprocal Rank Fusion）只用名次，鲁棒、免调参：

RRF(d) = ∑i∈系统 1k + ranki(d) k 常取 60

名次越靠前贡献越大；多路都靠前的文档被显著抬升。下面用真实数字算一遍。

例 · RRF 融合手算（k = 60）

query 同时走向量和 BM25 两路，各自 Top-3 名次如下：

文档向量路名次BM25 路名次RRF 计算RRF 分
d_A131/(60+1) + 1/(60+3) = 0.01639 + 0.015870.03227
d_B211/(60+2) + 1/(60+1) = 0.01613 + 0.016390.03252
d_C3—1/(60+3) + 0 = 0.015870.01587
d_D—20 + 1/(60+2) = 0.016130.01613
// 融合后排序（RRF 分从大到小）
1. d_B  0.03252   // 两路都靠前 → 升到第一
2. d_A  0.03227   // 一路第一但另一路才第三 → 屈居第二
3. d_D  0.01613   // 只在 BM25 出现
4. d_C  0.01587   // 只在向量路出现

直觉RRF 奖励"多路共识"：d_B 没在任何单路拿第一，却因为两路都靠前而综合最优 —— 这正是混合检索想要的鲁棒性，且完全不需要校准两路分数的量纲。

例 · Rerank 把"召回对但排不对"翻转过来

召回阶段（bi-encoder，§7 工程实践里有 bi vs cross 全对比）给出 Top-5 的粗排；cross-encoder 把每个 (query, doc) 拼一起重新精打分：

文档召回 cosine（粗排序）Rerank 分（精排序）名次变化
d10.82　（第 1）0.91　（第 2）1 → 2
d20.80　（第 2）0.45　（第 4）2 → 4 ↓
d30.79　（第 3）0.88　（第 3）3 → 3
d40.78　（第 4）0.30　（第 5）4 → 5 ↓
d50.77　（第 5）0.95　（第 1）5 → 1 ↑↑

最佳答案 d5 在召回里只排第 5（差点被 Top-k 截掉），cross-encoder 因为能让 query 和 doc 互相 attention，把它精排到第 1。代价：cross-encoder 每个 pair 都要跑一次前向、不能预编码，所以只对召回 Top-50/100 重排，不能当召回用。

召回侧全链路：从 query 到喂进 LLM（"缝合答案"）

最后一格："喂给 LLM" 不只是塞文本

  • 每个 chunk 带 来源标记（doc id / 标题 / URL），让模型能引用、可溯源
  • 放进 system / user prompt，明确指令"只依据下面证据回答，不足就说不知道" → 抑制幻觉
  • lost-in-the-middle：长上下文里中间内容易被忽略 → 最相关的放头/尾
  • token 预算：Top-k 与 chunk 大小要乘起来卡住上下文窗口

工程旋钮（面试常问"怎么权衡"）

  • 召回 Top-N（给 rerank 的候选数）：N↑ 召回率↑、rerank 延迟线性↑（典型 50~100）
  • rerank 后 Top-k（进 prompt）：k↑ 信息全但稀释 + 烧 token（典型 3~8）
  • RRF 的 k：默认 60，调小更偏信头部名次
  • rerank 模型：bge-reranker-v2 / Cohere Rerank / Jina Rerank

从"筛出来的向量"到 LLM 读懂 —— 实际代码与参数（破一个常见误解）

先纠正你问"筛选出来的文本向量怎么传给 LLM"——向量根本不传给 LLM。embedding 向量只在检索阶段当"地址/钥匙"用：拿它在向量库里定位到对应的 chunk。真正拼进 prompt、送进 LLM 的，是那个 chunk 的原始文本（就是 §1 入库时 payload 里存的 text）。LLM 从头到尾没见过 768 维向量，它只读文本。

完整 RAG 调用伪代码（含真实参数）

def rag_answer(question: str) -> str:
    # 1. query 向量化（必须和入库用同一模型、同样 normalize）
    qvec = embedding_model.encode(question, normalize=True)

    # 2. 检索：库返回 (score, payload)，payload.text 就是 §1 存的 chunk 原文
    hits = vector_db.search(qvec, top_k=50, ef_search=128)   # §5 的 HNSW 旋钮
    #（可选）再跑一路 BM25，RRF 融合 —— 见本节上半部分

    # 3. Rerank：cross-encoder 精排，取前 5（本节中段）
    pairs  = [(question, h.payload["text"]) for h in hits]
    order  = sorted(zip(reranker.predict(pairs), hits), key=lambda x: -x[0])
    top    = [h for _, h in order][:5]

    # 4. 缝合：把 chunk 原文 + 来源编号拼成 context 字符串
    context = "\n\n".join(
        f"[{i+1}] (来源: {h.payload['title']})\n{h.payload['text']}"
        for i, h in enumerate(top)
    )
    # token 预算：5 × ~500 ≈ 2.5k context，须 ≤ 模型窗 − system − 历史 − max_tokens

    # 5. 组 messages，调 LLM —— 注意：传的是 context 文本，不是向量
    resp = llm.chat(
        model="claude-haiku-4-5",        # 或 deepseek-chat / gpt-4o-mini
        messages=[
            {"role": "system", "content":
             "你是知识助手。只能依据 <context> 内的资料回答；"
             "无依据就答『资料中未提及』；每个论点后用 [n] 标注来源。"},
            {"role": "user", "content":
             f"<context>\n{context}\n</context>\n\n问题：{question}"},
        ],
        temperature=0.1,     # RAG 要忠于资料、抑制发挥/幻觉；0 也常见
        max_tokens=1024,    # 回答长度上限，控成本与啰嗦
        top_p=1.0,
    )
    return resp.content      # 形如 "长按 reset 键 10 秒…[1][3]"

参数为什么这么设（面试会追问）

参数取值 / 理由
检索 top_k50 · 给 rerank 的候选池，小了漏召回、大了 rerank 慢
rerank 后取5 · 进 prompt 的证据数，权衡信息量 vs token/稀释
temperature0.1 · 忠于资料不创作；要确定性可设 0
max_tokens1024 · 防啰嗦控成本，按答案长度调
context 顺序rerank 第 1 放最前/最后（lost-in-the-middle）

context 长度怎么卡（实际算一次）

context 预算 = 窗口 − system − 对话历史 − max_tokens 
# 大窗模型（如 200k）：基本不用担心
# 小窗模型（如 8k）：
8000 − 200 − 0 − 1024 ≈ 6776 token 留给 context
6776 / 5 chunk ≈ 每块上限 ~1355 token
# → 反推 §1 的 chunk_size 不能设太大！

闭环chunk_size、top_k、LLM 上下文窗必须一起算账 —— 这就是 §1 分块与 §6 缝合互相牵制的工程闭环。

工程实践 —— 选型、维度、归一化、pooling、踩坑

主流 Embedding 模型（中文 RAG 常用）

模型维度特点适用
BGE-large-zh / bge-m31024中文最常用；bge-m3 同时出 dense+sparse+ColBERT 多向量中文 RAG 首选，可单模型做混合检索
multilingual-e5-large1024需要加 "query:" / "passage:" 前缀指令多语言、跨语言检索
gte-Qwen2 系列1536+LLM 架构、last-token pooling，效果强但重追求精度、算力充足
OpenAI text-embedding-31536 / 3072API；支持 Matryoshka 截断降维不想自托管、快速落地

选型口诀先看语言（中文优先 BGE）→ 看是否要混合检索（bge-m3 一站式）→ 看维度与存储成本 → 用自己业务的真实 query 跑一遍 recall@k 再定，别只看 MTEB 榜单。

维度怎么选

  • 维度 ↑ → 表达力 ↑、召回 ↑，但存储/内存/检索延迟全部线性 ↑（1 亿条 ×1024 维 ×4B ≈ 400 GB）
  • Matryoshka 表示：训练时让前 k 维就能用，线上按需截断（如 1024→256）省 4× 存储，召回只掉一点
  • 原型期 384/768 足够；上规模再权衡量化（PQ / int8）

归一化 & pooling 的工程纪律

  • 入库和查询必须用同一个模型、同一种 pooling、同样是否归一化 —— 不一致是线上检索"全是噪声"的头号原因
  • 建议统一 L2-normalize + 内积索引（等价 cosine，且向量库最优化）
  • E5 / instructor 类模型必须加指令前缀，漏了会显著掉点

高频踩坑（面试 & 实战都问）

坑现象解法
query/doc 模型不一致检索结果像随机同模型同配置；端到端冒烟测试
分块（chunking）太大/太小太大稀释语义、太小丢上下文按语义/标题切，200–500 token + overlap，实测调
纯向量召不回专有名词/数字/型号"iPhone 15 Pro" 类精确词丢失混合检索：向量 + BM25，用 RRF 融合
Top-k 里有相关但不是最佳答案在第 8 名而非第 1Rerank：cross-encoder 对 Top-50 重排取前 5
各向异性 / 维度坍缩所有句子 cos 都 0.9+，区分度差选经对比学习的 embedding 模型，别裸用 BERT mean-pool
长文档超出 max length尾部内容没进向量分块入库；或选长上下文 embedding

bi-encoder vs cross-encoder —— 为什么需要两段（召回 + 精排）

离线预编码、建索引 ✔ 亿级也能毫秒召回　✘ 精度有上限 Cross-Encoder（Rerank） (q, d) 拼一起进模型 → 直接出相关性分 每个 pair 都要跑一次，无法预编码 ✔ 精度高　✘ 慢，只能排几十条 →

结论：Embedding（bi-encoder）负责从海量里快速召回 Top-50/100，Rerank（cross-encoder）负责在这几十条里精排 Top-5。两者不是替代关系，是 RAG 检索的两段式标配 —— 这正是 JD"混合检索、Rerank"想考的工程认知。

落地实战 —— 给定一个定死的 Embedding 模型，从 0 搭一套生产级 RAG

场景设定（具体项目）

项目：企业内部「IT 运维知识库问答助手」。数据源 = Confluence 导出 + 设备 PDF 手册 + 历史工单。Embedding 模型已被定死、不可更换、不可微调：

模型属性（定死）它强制决定了什么你被迫的应对
维度 d = 1024向量库 schema、存储 / 内存成本、索引参数先估容量；规模大再上量化（§5 PQ）
max_seq_len = 8192chunk_size 的硬上限chunk_size 取 256–512 ≪ 8192，留余量
自带 tokenizerchunk 长度只能用它来数length_function = 该 tokenizer.encode
需 instruction 前缀query / passage 必须各自加前缀入库加 "passage: "、查询加 "query: "，漏了显著掉点
相似度 = cosine向量库索引度量、是否归一化入库&查询都 normalize=True，库用内积/cosine 索引
不可 fine-tune召回质量的天花板就是这条线只能靠 chunking / 混合检索 / Rerank / query 改写来补 —— 这就是为什么后面那些环节都必须做

工业落地的核心逻辑模型被冻结 → 所有可调的质量杠杆都转移到模型周围的管线（分块、混合、重排、query 改写、评估迭代）。"定死 embedding"反而简化了一件事：换模型=全量重灌索引，既然不换，索引版本绑定就稳定了。

工业界一定会拆成两条独立管线

离线索引构建（文档变更时跑，慢、批量、可重算）与在线查询（每次请求跑，毫秒级、只读）必须分开。两者通过共享的索引存储连接。

落地骨架代码（把 §1 / §5 / §6 串成一个项目）

# 全局：模型定死，作为常量注入，离线/在线必须用同一个
EMB = load_embedding("bge-m3")        # 定死、不可换、不可微调

# ---------- 离线：建索引（文档新增/变更时跑）----------
def ingest(docs):
    for doc in docs:
        text = clean(parse(doc))                          # 解析+清洗
        for i, ch in enumerate(split_text(text,           # §1 分块
                          chunk_size=512, chunk_overlap=64,
                          length_function=EMB.tokenizer)):
            vec = EMB.encode("passage: " + ch,            # 模型要求的前缀
                             normalize=True)                 # 度量=cosine 必须归一
            vstore.upsert(id=f"{doc.id}#{i}", vector=vec,   # §5 向量+payload 同存
                          payload={"text": ch, "title": doc.title,
                                   "source": doc.url})
            bm25.add(f"{doc.id}#{i}", ch)                  # 同时进 BM25 倒排

# ---------- 在线：一次查询 ----------
def query(q):
    qv     = EMB.encode("query: " + q, normalize=True)  # 同模型+query 前缀
    dense  = vstore.search(qv, top_k=50)                  # §5 向量召回
    sparse = bm25.search(q,   top_k=50)                  # 关键词召回
    fused  = rrf(dense, sparse, k=60)[:50]                # §6 融合
    top    = rerank(q, [vstore.get(h.id).payload["text"]  # §6 精排
                        for h in fused])[:5]
    ctx    = build_context(top)                            # §6 拼上下文
    return llm.chat(system=GROUNDED_PROMPT,
                    user=f"<context>{ctx}</context>\n{q}",
                    temperature=0.1, max_tokens=1024)

关键不变量EMB 在 ingest() 和 query() 里是同一个实例、同样的前缀规则、同样 normalize=True。这是整套系统正确性的第一前提，比任何调参都重要。

工业排期：里程碑顺序（先基线跑通，再逐级增强 —— 呼应全文叙事）

阶段做什么完成标志 / 对应章节
P0 选型冻结确认 embedding 定死，据此定 chunk_size、向量库、度量、前缀规则参数全部写进配置常量（本节首表）
P1 离线管线 MVP跑通 ingest()：少量文档解析→分块→入库能在库里 get(id) 查到 chunk+payload（§1 §5）
P2 在线纯向量基线query→embedding→ANN→Top-k→LLM，先不加混合/rerank能出带引用的答案（= §4 基线跑通）
P3 加混合 + Rerank并上 BM25 腿、RRF、cross-encoder 精排专名/数字类 query 召回明显改善（§6）
P4 评估集 + 调参建 golden set（真实问题→正确文档），离线 recall@k / nDCG，端到端 faithfulness有数字可比，调 chunk_size/top_k/rerank 候选数
P5 上线 + 监控迭代增量索引、版本绑定、P99 延迟、成本、用户反馈回流线上指标可观测、可灰度、可回滚

为什么是这个顺序P2 先用纯向量基线（§4）打通端到端，能最快验证"数据/分块/前缀/库"没接错；之后每加一层（P3 混合+rerank、P4 评估）都是在可工作的系统上做增量，出问题能立刻定位是哪一层引入的 —— 这就是工业落地不一上来就堆全功能的根本原因。没有 P4 评估集，就不算"落地"，只是"能跑"。

必背公式（能默写）

  • 管线：tokenize → transformer → pooling → L2 norm

高频追问 & 标准答法

  • 为什么不用 BERT 直接 mean-pool？未经对比学习，空间各向异性、区分度差。
  • cosine 还是 dot？文本检索用 cosine（长度无关）；归一化后用 dot 等价且更快。
  • 向量召回 + 关键词为什么要混合？向量擅长语义、弱于专名/数字；BM25 反之；RRF 融合互补。
  • Rerank 为什么不直接当召回？cross-encoder 不能预编码，亿级跑不动，只能精排几十条。
  • temperature τ 的作用？调节对难负例的惩罚锐度，τ 小→梯度更尖锐。
  • 维度越高越好吗？表达力↑但成本线性↑；Matryoshka 可按需截断。

把 JD 那句话翻译成人话（面试可以直接背这段）

"了解 Embedding 模型原理与应用" —— 知道它把文本映射到语义向量空间，靠对比学习训练，用余弦度量相似度，是 RAG 的入口。

"熟悉向量数据库使用" —— 知道它存归一化向量、用 HNSW/IVF-PQ 做近似最近邻，在亿级规模下毫秒召回 Top-k。

"了解知识召回策略（混合检索、Rerank）" —— 知道纯向量召回有盲区，要用「向量 + BM25 经 RRF 融合」补专名，再用 cross-encoder Rerank 精排，最后把 Top-k 证据喂给 LLM 生成答案。

一句话总纲Embedding 把"找相关"变成"找最近邻"；向量库让最近邻在亿级数据上变快；混合检索 + Rerank 让召回结果变准 —— 三者合起来就是 RAG 的检索侧。
