⚙️ 从 JSON 到 invoke LLM — 引擎内部到底怎么跑的

可互动讲解 · 回答你的四个问题：每个 agent 有自己的上下文吗、系统怎么启动一个 agent、页面设置对应框架哪部分、一条数据怎么从 JSON 走到真正调用大模型。全部对着你仓库里的真实代码讲，点开自己玩。

30 秒电梯版
你在网页上编两份东西：①「工作流」（谁先谁后、循环几遍、并行还是路由）存进 workflows.json；②「智能体」（每个角色用什么模型、什么人设、能不能查知识库）存进 agents.json。两份靠一个名字接头（工作流里写 agent:"doctor"，引擎就去智能体表找 doctor）。跑起来时，引擎照着工作流一步步走，每一步 = 把变量拼进一段话 → 找到对应 agent → 让它 .send() → 这一 send 最终落到一行 chat.completions.create()，也就是真的发一次 HTTP 请求给 DeepSeek。每个 agent 有自己私有的记忆本，彼此只通过一块公告板（变量池）传结论。下面每一块都能点。

🩺 比方：医生（模型）不是张口就答。他先说"等下，我查一下资料库"（tool_call），助手（框架）把资料递给他，他看完才下结论。这一"查了再答"可能来回好几轮，直到他不再要资料、直接给结论为止。你在流程图上只看到"诊断"一格，其实里面是 2-3 次 API 往返。

  
🔧 技术细节：Agent.send 里有个 for _ in range(max_rounds) 循环（第 190 行）。每回合 client.invoke；若返回带 tool_calls → dispatch_all 跑工具、结果 append 回 messages、进下一回合；若没有 tool_calls → 这就是最终自然语言，返回。工作流节点用的 tracking_build_agent（factory.py）在 send 外包了一层：扫本轮新增的 retrieve 工具结果，抽成 references 事件——这就是患者镜头里"照护参考了哪份资料"的来源。

⑧ 速答卡


两个 agent 会"串味"吗——一个的对话跑进另一个？
不会。每个 agent 有独立的 self.messages，物理隔离。它们之间只通过变量池传字符串成品（A 的输出写进 context["A"]，B 的 prompt 用 {A} 取）。B 永远看不到 A 的对话历史，只看到 A 的最终那段文本。


循环里的 verifier，每轮都是新建的吗？
不是。同一次 run 内，同名 agent 只 build_agent 一次并缓存复用。所以循环第 3 轮的 verifier 记得自己前两轮说过什么——它的 self.messages 一直在累积。这也是为什么"辩论第 3 轮的 critic 记得前两轮"（引擎 docstring 原话）。


并行（parallel）时如果两个子步骤用同一个 agent 名会怎样？
校验器直接拒绝。validate_spec 要求 parallel 的子步骤 agent 名互不相同——因为同名共享同一实例，多线程并发写同一个 self.messages 会竞态。想并行就给不同名字（= 不同实例，各写各的）。


workflow 想换个模型跑，要改代码吗？
不用。改 agents.json 里那个 agent 的 provider/model 即可（Agents 页）；或整体默认在设置页改 config_store。工作流的 agent:"doctor" 一个字不用动——拓扑和节点身份是解耦的。


prompt 里的 {xxx} 写错了会怎样？
render_template 当场报错：模板变量未定义: {xxx} — 当前可用: [complaint, triage, …]，并把变量池里有哪些能用列给你。它只认裸名字，{a.b}/{a[0]} 不解析；要字面花括号用 {{ }} 转义。
