🔬 数据流显微镜 — 两个"怎么"

系列第四篇。这次对准两个最容易想歪的机制，先给一句话答案，再让你亲手拨动数据看它流动。

Q1 · agent 怎么知道该启动哪个工作流？
没有分类器、没有关键词匹配代码——run_workflow 工具的描述文字里印着一份工作流目录（id+输入名+名称），这份目录随每一次 LLM 请求寄出。是模型自己读目录、对号入座、从你的话里抽取输入填单。 服务员的随身手册里印着套餐菜单。客人说"来个双视角的"，服务员翻手册对上"双视角并行综述"，把客人的问题抄进点单栏——判断力在服务员（模型）脑子里，不在收银机（代码）里。
Q2 · 工作流里 agent 之间怎么传消息？
就是字符串替换进提示词。上一步的输出存进变量池 context[步骤id]；下一步的 prompt 模板里 {diagnosis} 这种占位符被整段原文替换，渲染结果作为一条普通 user 消息发给下一个 agent。agent 之间零直连——变量池+模板是唯一的桥。 厨师们从不隔灶台喊话：做完把成品贴到公告板（变量池），下一位的菜谱上写着"取板上的{诊断}"，他抄进自己的工作单再开工。

③ 三条底层真相（对照真实源码）

1 · 传递 = 渲染 + send，就两行
# workflow.py — 所谓"消息传递"的全部实现 prompt = render_template(step["prompt"], context) output = node(step["agent"]).send(prompt) context[step["id"]] = output # 回流入池, 同名覆盖
2 · agent 之间零直连
doctor 从没"听见"triage 说话——它只是收到了一条 user 消息，里面恰好抄着 triage 的输出。两个 agent 的笔记本完全隔离；跨 agent 的信息想过去，必须走 池→模板 这一条明桥。好处：每一步收到什么、依据什么，全部可审计（RUN HISTORY 里的原文就是证据）。
3 · 同一 agent 跨轮有两条通道
修订轮的 doctor 是同一个实例（节点缓存），所以它有：①自己的私有记忆（上一轮完整对话还在笔记本里）+ ②模板注入的 {review}（池通道）。这就是为什么修订版能"逐条回应"核验意见而不需要把初诊全文再喂一遍。
