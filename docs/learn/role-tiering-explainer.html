🎭 三视角分级 — 这两天到底做了什么

可互动讲解 · 用生活比方教你看懂：数据怎么流、变量怎么隔离、和之前比改了什么。不需要任何前后端知识，点开每个方块自己玩。

30 秒电梯版
你的健康 App 本来是所有人看到同一个界面（波形图、终端、配置全摊开）。这两天做了三件事： ①上锁（先把后端的"门"从街上改到只对内院开，再加登录）；②发防伪工牌（每个人拿一张签了名、改一个字就失效的通行证，后端逐一验它）；③按身份分家——患者看温柔的健康页、医生看临床台、开发者看全部机器；而且同一件事对三种人有三种说法（患者听"照护进行中"，医生看"诊断推理"，开发者看"step diagnose"）。下面每一块都能点着看。

① 三道门：请求是怎么被一层层拦下的

一个"请求"就是你的浏览器向后端要东西（比如"给我所有病人的会话记录"）。之前它畅通无阻。现在要过三道门。点下面的按钮逐层装门，看同一个请求发生什么。

🏠 比方：后端就像一栋放着病历的办公楼。M0 绑本机= 把所有门从"临街可推开"改成"只有内院（本机）能进" —— 隔壁网络的陌生电脑连门都摸不到。M1 登录门= 进楼要刷卡（登录拿工牌）。M2 验工牌= 每层楼的保安还会验你工牌是不是真的（下一节讲为什么工牌能防伪）。
🔧 技术细节：M0 = 三个后端服务（:8100 智能体 / :8080 传感器 / :3000 网关）从 0.0.0.0（所有网卡）改绑 127.0.0.1（只本机）。还堵了一个隐蔽洞：前端开发服务器的 host:true 会让局域网设备借它的"内网身份"转发进后端——等于白绑，也关掉了。M1/M2 是每个请求进后端先过一个中间件（middleware，像安检口，所有请求必经）。

② 工牌为什么能防伪 —— 而且为什么"界面藏起来"根本不算锁

登录成功后你拿到一张 token（通行证）。它长这样，点开看它怎么防伪：

身份信息（谁都能看，甚至能改）：
{"role":"patient","id":"P-001","name":"陈阿姨"}
防伪签名（服务器用密钥算出的指纹）：
a3f9c1…（和上面的身份严格对应）
🖊️ 比方：工牌上印着你的名字和职位（身份信息，谁都能照着改）。但角落有一个骑缝章，是保安处用只有他们有的印泥盖的，且这个章的花纹是照着你的名字职位算出来的。你把"患者"涂改成"开发者"——名字变了，但骑缝章还是旧的，对不上，保安一眼看穿：假牌！你没有那盒印泥，永远盖不出配套的新章。
🔧 技术细节：token = 身份(base64) . HMAC-SHA256签名。签名 = 用服务器密钥（存在 auth_secret 文件）对身份算的哈希。服务器每次收到 token，用同一把密钥重算签名，对不上就是伪造（返回 401）。密钥你拿不到，所以改了身份签名必然对不上。关键推论：前端把菜单藏起来 ≠ 安全 —— 你随手改浏览器里存的角色、或干脆绕过界面直接发请求，前端拦不住；只有后端每个请求都验这张签名工牌，才是真锁。这就是为什么这两天既做了前端隐藏（防手滑误点），又做了后端验签（防真越权）。

🔧 技术细节：每条会话/运行记录多存了一个字段 owner（创建时记下"这是谁的"）。查询端点在返回前加一道筛子：_owner_filter(request) —— 如果你是患者，只返回 owner == 你的编号 的；医生/开发者返回全部。你的编号从验过的工牌里读（挂在 request.state.user_info），你伪造不了。所以隔离不是"前端不显示"，是后端根本不把别人的数据发给你。旧的、没记 owner 的老数据，患者严格看不到（宁可少给，不漏给）。

④ 两个"归属"标签：谁在操作 ≠ 为谁操作

这里有个精妙处，也是照护丝带能跑通的关键。一次"分析"有两个主角，得用两个标签分开记。

🩺 医生点了"发起分析"
——为——>
🌿 陈阿姨 P-001这次分析是给她的
这一次运行记了两个标签：
· owner = doctor —— 谁发起的（操作者）
· patient_id = P-001 —— 为谁跑的（服务对象）
💊 比方：护士给 3 床病人取药。操作者是护士（她刷的卡、她负责），服务对象是 3 床病人。如果只记"护士取了药"，病人自己永远查不到"有人在为我准备药"。所以要单独记为谁。患者今天页的照护丝带，查的是"为我（patient_id）跑的分析"——哪怕是医生发起的，她也看得到。而医生自己的"我发起过哪些"，查的是 owner。两个维度，各管各的。
🔧 技术细节：owner 管"我的会话/我发起的运行"（第③节的隔离）；patient_id 管"为这个病人跑的照护"（照护丝带 care_ribbon_for(patient_id) 用它查）。医生发起时前端把 patientId=选中病人 塞进请求，后端 run 同时记下 owner 和 patient_id。少了这个区分，患者今天页就只能显示"自己亲手发起的"（她从不发起）→ 永远空白。

⑤ 三镜头：同一件事，对三种人三种说法

这是整个设计最漂亮的一点，也是你问的"数据流向"里最有意思的分叉。同一次分析运行，产生同一串事件；切换你的身份，看这串事件被翻译成完全不同的样子。

🏥 比方：一台手术正在进行。护士对着等候区的家属广播："手术进行中，一切顺利"；对着主刀医生的记录写："正在分离粘连、探查病灶"；对着器械技师喊："step 3，递止血钳"。同一台手术，同一时刻，三种说法——不是三台手术，是同一件事的三层翻译。你的健康 App 里，一次分析的每一步都预先写好了三种文案，系统按你的身份挑一种给你看。
🔧 技术细节：工作流的每一步（step）除了给 AI 的指令，还带一个可选的 labels: {patient, doctor} 字段。运行时这些文案跟着事件流一起送出来（step_start/step_end 事件带 labels）。前端按你的角色投影：患者取 labels.patient（"正在了解你的情况…"），医生取 labels.doctor（"诊断推理"），开发者不翻译、看原始 step id + agent。引擎本身不消费 labels，只透传——所以给旧工作流加 labels 完全不影响它跑，是向后兼容的纯装饰层。

⑧ 速答卡

"前端隐藏"和"后端验证"到底差在哪？为什么两个都要做？
前端隐藏 = 把菜单项藏起来，防手滑（患者不会误点到危险按钮），但改浏览器数据或绕过界面就破了。后端验证 = 每个请求验签名工牌 + 查权限表，防真越权（哪怕你直接发请求也被拒 403）。前者是体验（干净不吓人），后者是安全（真锁）。这两天先做前端（M1）再补后端（M2），并且明确告诉过你：只做前端时不能说"患者无法访问"，因为那不是真锁。
"中间件"是什么？为什么所有请求都要过它？
想象大楼只有一个安检口，进楼的每个人（每个请求）必经。中间件就是这个安检口的代码：它在请求真正到达"办事窗口"（具体接口）之前，先验工牌、查这个人能不能办这件事、给患者的敏感请求还会剥掉危险参数。放行了才往里送，不放行直接 403 打回。好处：安全逻辑集中在一处，不用每个窗口各写一遍。
"运行时数据不进 git" 是什么意思？种子（seed）又是干嘛的？
代码进 git（版本库），但密钥、病人数据库、工作流定义这类"每台机器自己的东西"不进（写在 .gitignore 里，避免泄漏 + 避免机器间打架）。可这带来一个问题：新工作流 followup_review（医生"发起分析"要用）写在不进 git 的文件里，别的机器就没有它。种子解决这个：程序第一次启动时，发现缺这个工作流就自动补上（像新手机首次开机自带几个默认 App）。已经有了就不动，尊重你的修改。
为什么"发起分析"要新建 followup_review，不直接用现成的 clinic_sim？
clinic_sim（模拟问诊）中间有一步要真人回答（患者扮演回答分诊问题）。如果医生一键发起后就走开，工作流会卡在那一步干等，照护丝带就停住了。所以新建了 followup_review：纯 AI、没有需要真人的步骤，医生点完就在后台自己跑到底，丝带能完整走完"了解→对照资料→核验→完成"。clinic_sim 保留给需要真人互动的完整问诊场景。
数据"隔离"和"加密"是一回事吗？
不是。这两天做的是隔离（访问控制）：数据都在，但后端按身份决定发不发给你——像图书馆的书都在架上，管理员按你的借书证决定让不让你借某本。加密是另一件事（把内容变成密文，没钥匙看不懂）。密钥（auth_secret）本身是加密存的思路，但会话/病人数据的保护这两天靠的是隔离 + 后端绑本机，不是全盘加密。
