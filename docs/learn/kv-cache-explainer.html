⚡ KV Cache 与 Prompt Caching — 面试级技术总结

系列第五篇 · 面向面试场景：每个概念给中英术语、公式和数字；两个互动可以当场演示；结尾是追问速答卡。

30 秒电梯版 — 开场就背这段
LLM 推理分 prefill（并行处理全部输入、为每个 token 算出 attention 的 Key/Value 张量）和 decode（逐 token 生成）两阶段。KV 张量对相同的（输入 token 序列 × 模型权重）是确定性的，所以推理服务把它按内容寻址（分块哈希）缓存：下次请求只要前缀逐字节相同，直接复用 KV、跳过这段 prefill。由于 causal attention 里第 i 个 token 的 KV 依赖其前全部 token，缓存命中是"最长公共前缀"语义——变化点之后全部失效。工程含义：把稳定内容（system、工具定义）放序列前部、易变内容（时间戳、动态注入）尽量尾置。收益是三重的：省 prefill 算力（各家 API 缓存命中价约为原价 1/10~1/2）、降 TTFT（首字延迟正比于未命中 token 数）、这一切在无状态 HTTP 上照样成立。

① 两阶段推理 prefill vs decode

Prefill（预填充）compute-bound 算力瓶颈

并行处理全部 N 个输入 token；attention 计算量 ~O(N²·d)；产物 = 每层每头的 K/V 张量（KV cache）。TTFT ≈ prefill 时间。
输入 token → 逐个算出 KV（蓝 = 已入缓存）

Decode（解码）memory-bound 带宽瓶颈

逐 token 生成；每步要从显存读出全部 KV cache + 权重做一次 attention——瓶颈是 HBM 带宽而非算力。TPOT（每 token 时延）由此决定。
生成 token（绿）逐个出现, 每个都要"回读"左边全部 KV
面试点: 为什么 prefill 吃算力、decode 吃带宽 — 前者大矩阵并行乘, 后者每步都要搬运整个 KV

③ 定量武器库 numbers you can cite

KV cache 每 token 占多大？（追问率极高）
bytes/token = 2 (K和V) × n_layers × n_kv_heads × head_dim × dtype_bytes 例: 32 层 · GQA 8 个 KV 头 · head_dim 128 · fp16(2B): = 2 × 32 × 8 × 128 × 2 = 128 KB / token → 50k token 的会话 ≈ 6.4 GB 显存 — 这就是为什么缓存有 TTL、 为什么 DeepSeek 把 KV 下沉到 SSD、为什么 GQA/MQA 存在（砍 n_kv_heads）。

④ 无状态 HTTP 上怎么实现 content-addressed caching

请求进来 → tokenize → 按块（block/page，数十到上百 token）计算链式哈希（每块哈希包含其前缀的哈希）→ 在缓存索引里找最长连续命中的块链 → 命中的块直接加载 KV 张量，只对剩余后缀做 prefill。

三个面试要点：①不需要会话 ID——按内容指纹归档，协议无状态但推理层有一个内容寻址的状态库；②集群要么做缓存亲和路由（把你路由到持有 KV 的机器），要么把 KV 放共享存储（DeepSeek 的 SSD 方案）；③改 temperature/top_p 不会破坏缓存（采样参数只作用于 decode 的 logits，不改输入 token），但改 system、改工具定义顺序、换模型版本都会——因为它们改了被哈希的 token 序列。

⑤ 追问速答卡 rapid-fire Q&A — 点开对答案

为什么 decode 是带宽瓶颈而不是算力瓶颈？
decode 每步只算 1 个新 token 的 attention——计算量很小，但必须把整个 KV cache 和模型权重从 HBM 搬进计算单元。搬运字节数 ≫ 浮点运算数，算术强度（FLOPs/byte）极低，GPU 算力空转等内存。批量推理（batching）与 PagedAttention 都是为了摊薄这个搬运成本。
为什么改前缀中间一个字，后面全部失效？
causal attention 下，第 i 个 token 的 K/V 由它及其之前所有 token 经各层变换算出。位置 k 变了 → 所有 i ≥ k 的隐状态与 KV 都变。所以缓存命中语义是最长公共前缀，块哈希做成链式（含前缀哈希）正是为了表达这一点。
GQA / MQA 和 KV cache 什么关系？
KV 大小正比于 n_kv_heads。MQA 所有 query 头共享 1 组 KV，GQA 分组共享（如 32 个 Q 头共享 8 组 KV）→ KV 显存直接砍到 1/4~1/32，代价是轻微质量损失。这是"为长上下文省 KV"的模型结构侧手段，与 prompt caching（服务侧复用）正交互补。
Anthropic 的 cache write 为什么要加价 25%？
写入意味着服务商要为你占住显存/存储并维护索引（TTL 内随时可读）——存储承诺有成本。定价设计成"写小贵、读大惠（0.1×）"：只有真的会被重复读的前缀才值得显式标记，引导用户把断点打在稳定前缀上。
怎么在 agent 系统设计里最大化命中率？
一条原则：让会变的东西尽量靠后站。具体：①system 与工具定义内容和序列化顺序都要稳定（别在 system 里放时间戳）；②动态上下文（时钟、传感器快照）附着在消息流尾部而非开头；③会话历史 append-only 不回改；④多 agent 场景让同类请求复用同一前缀模板。我在自己的项目里把动态注入设计成独立于 system 的注入层，正是为了保住 system+tools 这段最长稳定前缀。
本地部署（vLLM）和远程 API 的缓存有何异同？
机制同源：vLLM 的 Automatic Prefix Caching / SGLang 的 RadixAttention 就是同一件事的开源实现（PagedAttention 把 KV 切页、按哈希/基数树共享）。差异在受益者：本地省的是自己的 GPU 时间与并发容量；远程由服务商省算力、以 0.1×~0.5× 价格返还，且有 TTL 和（多数厂商的）租户隔离。
缓存命中对延迟的影响有多大？
TTFT ≈ 未命中 token 数 ÷ prefill 吞吐。50k 历史全命中时只需 prefill 新增几百 token——首字延迟从秒级降到百毫秒级，近一个数量级。对多轮 agent（每轮都背全量历史）这是体感差异最大的一项。
哪些常见操作会悄悄打破缓存？
①在 system 里嵌当前时间/随机 ID；②每轮重排工具列表（JSON 序列化顺序不稳定）；③框架自动改写历史（截断、压缩、注入位置前移）；④模型版本升级；⑤负载均衡把请求打到无缓存副本（无亲和路由时）。排查思路：对比相邻两轮请求体，找第一个差异字节的位置。

⑥ 把它讲成你自己的项目故事

面试官最爱的收尾：你在真实系统里怎么用它。可以这样讲——"我做了一个多 agent 的传感器平台，自研框架的消息装配是四层：system 人设、动态上下文注入、对话历史、新消息。设计注入层时我刻意不让动态内容进 system、也不落入持久历史（每轮现算、独立成一条带 <system-reminder> 标签的假 user 消息）——一是防指令混淆，二是保住 system+工具定义这段最长稳定前缀的 KV 缓存。后来我复盘缓存命中率，发现注入放 L2 会拖累整段历史的 KV——于是照 Claude Code 的 harness 布局把注入点挪到了尾部（插在最新 user 消息之前，特意避开工具轮的 tool 消息块以免破坏协议顺序），改完 system、工具定义、全部历史的前缀都能跨轮命中。多轮会话下，这一处装配顺序的改动在成本和首字延迟上差接近一个数量级。"
