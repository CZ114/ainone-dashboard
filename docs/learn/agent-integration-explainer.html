🍽️ 你的 Agent 是怎么接进前后端系统的？

全篇只用一个比方讲到底：整套系统 = 一家餐厅。你在 Music!!! 项目里训练的 agent 库是一位主厨，dashboard 这家餐厅把他"外聘"了过来。看完这页你会明白：你在网页上打一句话，它是怎么一路跑到主厨手里、又怎么变成屏幕上蹦出来的回答的。

🪑前端 = 餐厅大堂

你看得见、摸得着的一切：聊天框、按钮、设置页。它只负责"好看 + 收集你的操作"，自己不会思考。 大堂里的菜单、桌椅、服务员——但饭不是在这做的。（对应 frontend/ 文件夹，用 React 写的网页）

🍳后端 = 后厨

你看不见但真正干活的程序，在你电脑上默默运行。这家餐厅有好几个后厨，各管一摊（等下地图上见）。 点了菜之后所有的洗切炒炖——都发生在你看不到的地方。（对应 backend/ 文件夹）

🚪端口 = 门牌号

这些程序全住在你电脑这"一栋楼"里，靠数字门牌区分：5173、3000、8100、8080。给 8100 送单子，绝不会送错到 8080。 同一栋楼里的不同房间号。网址 localhost:5173 意思就是"本楼 5173 室"。

④ 为什么要隔这么多层？不能让网页直接找主厨吗？

1 · 前台没换人 → 随时能回退
迁移时的约定是"不动原版代码"。老前台（原来对接 Claude 的 :3000）原样留着，我们复制了一个新前台改成"只转单"。哪天想换回旧厨房，换个启动脚本就行，大堂完全无感。 餐厅换主厨没有装修大堂——客人第二天来，一切照旧，只是菜更合口味了。
2 · 主厨不用学接单 → 你的库保持纯粹
你的 agent 库里没有一行"怎么收网络请求"的代码——接单、排队、催菜全是 :8100 这个厨房（agent_service）的事，主厨只管一件事：拿到菜单，做菜（Agent.send()）。所以这个库明天还能被别的项目外聘。 主厨只练厨艺，不学收银。收银台换了牌子，主厨的手艺一点不受影响。
3 · 智囊是外包的 → 换 LLM 像换供应商
真正"想答案"的是远方的大模型。你的库把"寄信给谁"做成了配置（venice / deepseek / qwen…都行），设置页改一下，整个餐厅其它环节零改动。 今天用 A 家的高汤，明天换 B 家——菜谱和厨房流程一个字不用改。
